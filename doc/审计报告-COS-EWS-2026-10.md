## 1. COS 信任边界与密钥流复核

### 1.1 mail-worker 侧（全权子账号）

COS 的读写凭据（`bucket` / `endpoint` / `s3AccessKey` / `s3SecretKey`）存放在 **D1 `setting` 表**，由管理面板写入，运行时由 `settingService.query` 读取。

- 读取出口做**掩码**：`mail-worker/src/service/setting-service.js:76-79` 对返回值做浅拷贝后再掩码，避免就地污染 KV/`c` 中缓存的 setting 对象 ——

  ```js
  // 浅拷贝：掩码只作用于本次返回值，避免就地污染 c / KV 中缓存的 setting 对象
  const settingRow = { ...settingData };
  // resendTokens 是嵌套对象，掩码前单独拷贝，避免污染缓存中的原对象
  settingRow.resendTokens = { ...(settingRow.resendTokens || {}) };
  ```

- 掩码作用于 `siteKey` 与 `resendTokens` 的子值（`setting-service.js:87-88`）；`s3SecretKey` 类字段仅在 `showSiteKey=true` 的内部调用（`setting-service.js:200`）才返回原值，不经过任何面向普通用户的 API。
- 复核结论：**系统设置类接口不向普通用户泄露 COS 凭据**；D1 中的密钥只能通过 Worker 内部读取，浏览器侧永远拿不到。

### 1.2 cos-exchange Worker 侧（只读子账号 + CF Secrets）

`doc/cos-proxy-worker.js` 读取的凭据全部来自 **Cloudflare 环境变量/Secrets**（`env.AWS_ACCESS_KEY_ID` / `env.AWS_SECRET_ACCESS_KEY` / `env.S3_ENDPOINT` / `env.REGION`），并对取值统一 `trim()`（`doc/cos-proxy-worker.js:213`（S3_ENDPOINT）、`:222`（REGION）、`:226-227`（AK/SK））；缺失时直接 500 且不回显变量名以外的信息（`:213-225`）。

- 该子账号按前次审计结论为**只读**（仅 `/attachments/` 与 `/static/` 回源），本轮未改变其权限模型。
- 本轮新增的环境变量 `MAIL_ORIGIN`（默认值常量 `:22`，解析函数 `:24-32`）与 `BROWSE_DENY_PREFIXES`（默认值常量 `:1627`，解析函数 `:1628-1633`）**均非密钥**，只是域名/前缀配置，不构成新的密钥载体。
- 前次审计的硬编码域名问题本轮清零：跳转目标、Referer 白名单、ACAO 全部改为从 `mailOrigin(env)` 取值（`:284-286`、`:78-79`、`:173`）。

### 1.3 前端零密钥

`mail-vue` 侧不含任何 COS 凭据：附件访问走「后端签发短期签名 URL」（`mail-worker/src/utils/sign-utils.js` 的 `signKeys`/`signContent`），前端只接收 `att.url` 字符串（见 `doc/签名防伪造改造说明.md` 的既有结论）。本轮对 `mail-vue` 的改动仅限 `src/utils/sanitize-html.js` 的 URL 校验加固（复审再叠加 CSS 反斜杠清空，`sanitize-html.js:117-119`）与 i18n 文案，**未新增任何密钥读取**。

### 1.4 EWS 新增的服务端直读路径（本轮新增，重点复核）

这是本轮唯一新增的 COS 访问路径，性质与前两条不同：**不签发签名 URL，直接由 Worker 用自身全权凭据读取对象**。

| 环节 | 实现 | 行号 |
|---|---|---|
| 读取函数 | `r2Service.getObj(c, attRow.key)` | `mail-worker/src/ews/handlers.js:275`（MimeContent 重建）、`:689`（GetAttachment） |
| 归属前置 | 读之前必须先按 `att.userId = 当前用户` 命中行 | `:259`（`attachmentRows(c, row.emailId, row.userId)`）、`:677-683` |
| 大小前置 | 超过 `maxAttBytes` 的行**不进读取分支** | `:266`（重建时跳过）、`:684-687`（GetAttachment 直接 Fault） |
| 总量前置（复审轮新增） | 跨本次响应累计的附件字节账本 `attBudget` 超 `ewsMaxTotalAttBytes` 后同样跳过不读；MimeContent 请求的 Id 集先 clamp 到 ≤`EWS_MAX_MIME_ITEM_IDS` | `:253-255`、`:267-274`（账本判定与跳过）、`:633-636`（GetItem clamp+账本）、`:588-591`（SyncFolderItems 同款） |
| 失败语义 | 对象不存在 → Fault，不回显 key/桶信息 | `:689-692` |

**判定**：该路径没有把「读 COS 的能力」暴露给客户端 —— 客户端提交的是 **附件 ID（`att.attId`）**，不是对象 key；`attId → key` 的映射只存在于服务端 D1，且查询强制绑定 `userId`。因此不存在「客户端指定任意 key 让服务端代读」的 SSRF 式滥用面。密钥流与 §1.1/§1.2 一致，**未新增**。

复审轮补入的字节账本（`attBudget`）不改变密钥模型：它只限制**本次响应允许重建多少附件字节**（响应级配额），账本自身不含任何凭据，也不产生新的 COS 读取入口；超限附件走「跳过」路径（客户端可按需用 `GetAttachment` 单取或改走 Web 端）。

> 补充说明（与签名链的关系）：EWS 直读**绕过了** `cos-exchange` 的验签层，但这是设计意图（服务端到服务端，无浏览器参与）。绕过验签的代价由 §3.2 的归属校验补偿。

> EWS 端点：`POST /EWS/Exchange.asmx`（大小写不敏感）。入口拦截 `mail-worker/src/index.js:12-13`、`:19-22`，常量 `mail-worker/src/ews/const.js:9`。

#### 3.3.1 物理删除 tombstone（复审轮新增）

**问题**：增量同步靠 `update_time` 水位扫描**尚存的行**。附件彻底删除（`att-service.js:651`）、7 天自动清理（`:745`）、后台批量删除（`email-service.js:1290`）、删账号（`:1310`）都是**物理删除**——行一消失，增量扫描就再也看不到它，客户端不会收到 `<t:Delete>`，表现为「幽灵邮件」（点开报错、计数不一致），且 30 天内都不会自愈。

**处置**（表由 v4_4DB 建，`mail-worker/src/init/init.js:276`）：

| 环节 | 实现 | 行号 |
|---|---|---|
| 写侧登记 | `insertEwsTombstones` 在**删行前**按 ≤90 分片 `SELECT` 待删行并 `INSERT OR IGNORE`（写入失败仅告警，不阻断删除） | `email-service.js:43-67`、`att-service.js:41-65` |
| 写侧挂载点（5 处） | physicsDelete / batchDelete / physicsDeleteByAccountId / deleteEmailsWithoutAtt / clearTrash | `email-service.js:975`、`:1290`、`:1310`；`att-service.js:651`、`:745` |
| 写侧豁免 | `physicsDeleteUserIds`（用户整体删除）**不登记** —— 用户删除后其 EWS 认证即失效，事件无意义 | `email-service.js:981-986` |
| 读侧产出 | 增量阶段 `del_time > 本轮进入时的水位` 的行 → `<t:Delete>`；与同轮已产出的 ItemId 去重；历史积压翻页中不产出（避免跨轮重复） | `handlers.js:373-385`（读）、`:572-578`（选）、`:596`（输出） |
| 文件夹映射 | `trash=1 → deleteditems`；否则 `type=0 → inbox`、`type=1 → sentitems`（与同一邮件在哪个文件夹可见的口径一致） | `protocol.js:290-295`、`:305-318` |
| 保留期与清理 | 保留 30 天，每日 cron 删除更早记录（失败只告警，不中断后续定时任务） | `mail-worker/src/index.js:95-101` |

**判定**：tombstone 是**读侧补偿**而非新增读能力——记录里只有 `(user_id, email_id, type, trash, del_time)`，无正文/附件信息；读侧仍按 `user_id` 严格绑定（`handlers.js:376-379`）。未迁移（表不存在）时读取被吞掉并返回空集，不影响其余同步（`handlers.js:381-384`，冒烟 #24 覆盖）。定级：**无新增攻击面**。

### 3.5 发信管线继承

`CreateItem` 不自行发信，而是调用 Web 端同一服务：

```
handlers.js:851  const result = await emailService.send(c, { accountId, name, sendType: 'send',
                                                          receiveEmail, subject, text, content: html,
                                                          attachments }, user.userId);
```

- `user.userId` 作为第 3 参数传入 —— 与 Web 端调用签名一致，**继承全套校验**（配额/限额/黑名单/发信服务选择，含 Resend / CF Email 分支）。
- 业务异常（`BizError`）转成 Fault 文案供客户端展示（`handlers.js:862-868`），内因不泄露。
- 收件人合并去重 `:832-838`；`cid:` 引用还原为 `data:` URL 后再交由既有附件管线（`:828-830`）。
- 附件总量阈值 `ewsMaxTotalAttBytes`（默认 2×单附件阈值，`const.js:43-47`）在 `handlers.js:764` 取值、`:823-826` 判定生效。
- 复审补充（P3-3）：`IsInline` 但类型非 `image/*`/`video/*` 的附件强制降级为普通附件（`protocol.js:360-364`），避免 `data:` URL 被发信清洗器删除后**附件静默丢失**。

**判定**：EWS 不构成「绕过发信风控」的旁路。唯一的差异是**附件大小更严格**（默认 1MB，见 §3.6），属收紧而非放宽。

**4.1 KV 最终一致（/temp 总量）**
KV 无原子自增，容量账本采用「账本 + 校准」两层（`doc/cos-proxy-worker.js:802-847` 一带）。并发上传时读-改-写存在窗口，实际占用可短暂超过设定上限。处置建议：维持现状（已在前次审计 §10.5 记录），如需硬上限需引入 Durable Object（成本上升，与 Free 计划冲突）。

**4.2 单 isolate 内存限流**
`doc/cos-proxy-worker.js` 的 `loginBlocked`/限流 Map 与 `mail-worker/src/ews/auth.js:33` 的失败 Map 都是 isolate 内存态，多 PoP 部署下每 isolate 独立计数。处置建议：维持现状 —— EWS 面另有「成功缓存（复审后加盐）+ 归属校验 + 1s 失败延迟」兜底，爆破成功仍需正确密码；且密码校验本身消耗 CPU，规模化爆破成本高。

**4.3 CF 压缩省略 Accept-Ranges**
Cloudflare 对压缩响应的头处理导致 `Accept-Ranges` 可能缺失，属平台行为。处置建议：记录已知，不改代码。

**4.4 KV namespace 混用**
`mail-worker/wrangler.toml:20-22` 绑定的 `kv`（id `2fe4f308…`）同时承担业务 KV 与 COS 故障时的附件回退存储（`mail-worker/src/service/kv-obj-service.js:3-4` 直接 `c.env.kv.put`）。风险：附件回退写入可能挤占业务 KV 的写入配额（1000 写/天），反之亦然；也影响故障排查时对数据归属的判断。处置建议（运维）：拆分为两个 namespace（`kv` 业务 / `kv_att` 回退）并改绑定名，**本轮未改**（涉及绑定名变更，需运维窗口）。同类：cos-exchange 的 `BROWSE_KV` 与 `TEMP_KV` 建议独立绑定（`authStore`/`tempStore` 优先级见 `doc/cos-proxy-worker.js:495`、`:522-527`，当前设计允许单 KV 混用）。

**4.5 TEMP_PASS 建议改 Secret**
`TEMP_PASS` 目前按普通环境变量使用（`doc/cos-proxy-worker.js:1185`、`:1212`），Cloudflare 面板中普通变量对账号内有权限者明文可见。处置建议（面板操作）：改为 Secret 类型（`wrangler secret put TEMP_PASS` 或面板加密变量），值本身不变。

**4.6 Resend webhook fail-closed 的部署前提**
`resend-service.js:70-73`：未配置 `RESEND_SIGNING_SECRET` 时**一律拒绝** webhook。安全上正确，但会让未配置该 Secret 的实例**丢失投递状态回写**（邮件状态停在已发送）。处置建议（部署清单项）：升级前先确认已配置该 Secret，否则投递失败/退信状态不再回写，见 §5.1。

**4.8 EWS 认证缓存窗口**
`ews/auth.js:9-11`、`auth.js:106-127`、`const.js:15-17`：成功认证按 `sha256(jwt_secret:email:password)` 缓存 **300s**（复审前为 900s 且未加盐），改密码后旧密码最长 300s 内仍可通过 EWS 认证（Web/JWT 侧不受影响，`README.md:200` 已明示）。处置建议：接受 —— 缓存 key 含 `jwt_secret` 加盐与密码哈希，改密码/封禁即产生新 key 或被拒绝路径主动删缓存，旧 key 最迟 300s 自然过期；TTL 已从 900s 收紧到 300s，再缩短会显著增加每请求的查库+哈希成本（Free 计划 CPU 约束）。

**4.9 自定义角色的附件权限需手工补（复审 P3-5）**
`mail-worker/src/init/init.js:225-246` 的 `v4_3DB` 只为**默认角色**（`WHERE r.is_default = 1`，`:245`）补 `att:query`/`att:delete`。若部署实例存在自定义角色（`is_default = 0`，常见于多租户/分级管理配置），升级后这些角色的用户访问 `/att/*` 会被 RBAC 拒绝（403）。处置建议（运维/面板操作）：升级后在「角色管理」中为每个自定义角色手动勾选「附件查看」「附件删除」两项；本报告不做代码改动（自动补全等于绕过管理员的权限意图），部署清单见 §5.1。

**4.10 UpdateItem 对非 IsRead 字段静默 Success（复审 P3-8）**
`handlers.js:898-908` 只处理 `message:IsRead`，其余 `SetItemField` 既不报错也不落库，随后照常回 `Success`（`:932`）。影响：客户端若尝试改主题/分类等字段会误判成功（实际未生效）。处置建议：接受 —— Thunderbird 145+ 实际只发已读标记；若要严格，可对未支持字段回 `ErrorInvalidPropertySet`（属行为收紧，需同步改客户端预期，后续如需再排期）。

**4.11 SendOnly 也保存副本（复审 P3-8）**
`handlers.js:742-746` 只拒绝 `SaveOnly`；`SendOnly` 与 `SendAndSaveCopy` 走同一路径，都会在「已发送」留副本（CloudMail 无 outbox 语义，发信由 `emailService.send` 一次完成）。处置建议：接受 —— 与 Web 端行为一致，且不发副本会让用户丢失已发记录。

**4.12 verifyPassword 的 `===` 比较（复审 P3-8）**
`crypto-utils.js:25-27` 用 `hash === storedHash` 比较（非恒定时间）。处置建议：接受 —— 该路径的输入需先经 Basic 认证解析与 KV/D1 查库，网络与哈希耗时远大于字符串比较差异；现实威胁模型外。若要统一口径可复用 `sign-utils.timingSafeEqual`，属可选加固。

**4.13 folderCounts 全表条件聚合（复审 P3-8）**
`handlers.js:200-207` 对 `email` 表按 `visibleFilter` 做 `COUNT(*)` + `SUM(CASE WHEN unread …)`，条件含 `userId/type/isDel/trash`。大邮箱（数万行）时 `GetFolder` 会比纯索引计数慢。处置建议：接受 —— 只在 `GetFolder`/`SyncFolderHierarchy` 触发（非高频），且后续可用 `(user_id, type, is_del, trash)` 组合索引或缓存计数优化。

**4.14 成功响应无 XML 声明 / Envelope（复审 P3-8）**
成功响应由 `operationResponse`（`xml.js:149-153`）直接输出 `<m:XxxResponse>`，没有 `<?xml …?>` 声明与 `<soap:Envelope>` 包裹（仅 Fault 经 `soapEnvelope`，`:125-131`、`:145`）。处置建议：接受 —— 既有行为，Thunderbird 145+ 实测正常解析；如需与规范严格对齐，可在 `operationResponse` 外包一层 `soapEnvelope`，属兼容性加固而非安全项。

**4.15 test/index.spec.js 无法运行（复审 P3-8）**
`mail-worker/vitest.config.js` 声明 `wrangler: { configPath: './wrangler.jsonc' }`，但仓库只提供 `wrangler.toml`，`vitest`/`@cloudflare/vitest-pool-workers` 启动即失败；`package.json` 的 `test` 脚本实际是 `wrangler deploy`（并非测试）。属**预先存在**的仓库环境问题，与本轮改动无关（复审期间以临时配置执行 `test/html-sanitize.spec.js`、`test/fallback.spec.js` 验证通过）。处置建议（后续排期）：补一份 `wrangler.jsonc` 或把 `configPath` 改指 `wrangler.toml`，并把 `test` 脚本改为真正的 `vitest run`。
